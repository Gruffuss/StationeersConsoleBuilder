# M6 — Send to chip, CI, the Pages deployment and the launch

This report covers the M6 plan.

## Game endpoint

Measured on 2026-10-12 against the owner's game, with StationeersLua 1.1.0.0 (its `initialize` answer's `serverInfo`) and ScriptedScreens Vector 0.11.118 (the first line of `vector_stats`; the plan's section 4 read 0.11.117 earlier that day), at `http://127.0.0.1:3030`. The game's `[MCP Server]` settings at the time had `AllowRemoteConnections = true`; the other settings that bear on chip access were not recorded. Every exchange is a fixture in `web/test/fixtures/game-mcp/` (the file names below), scrubbed as that folder's README says.

**Observed** (each in the fixture named):
- **JSON, not an event stream.** Every request offered `Accept: application/json, text/event-stream`; every answer with a body came back `Content-Type: application/json` with one JSON object (`s1-initialize`, `s1-tools-list`, `s4-*`). `notifications/initialized` is answered `202 Accepted` with an empty body and no content type (`s1-initialized`).
- **No session id.** No answer carried an `Mcp-Session-Id` header, `initialize` included (`s1-initialize`, `s3-post-with-origin`). The `tools/call` requests sent no `Mcp-Session-Id` and were answered (`s4-*`); requests that sent an empty `Mcp-Session-Id` were answered too (`s3-post-with-origin`, `s3-post-startup-timeout`).
- **The origin refusal.** An `Origin` not in `AllowedBrowserOrigins` is answered `403 Forbidden`, `Content-Type: application/json`, body `{"error":"Forbidden: browser Origin not allowed. Add it to [MCP Server] AllowedBrowserOrigins to permit."}`, with no `Access-Control-Allow-Origin` (`s2-origin-refused`). A preflight from such an origin gets the same 403 and body (`s3-preflight-before-restart`).
- **Host.** With no `Origin`, `Host: localhost:3030`, `Host: 127.0.0.1:3030` and `Host: example.test:3030` were all accepted with 200 (`s2-host-*`). No Host value was refused.
- **The allowlist needs a restart.** After the test origin was added to `AllowedBrowserOrigins` while the game ran, both the preflight and the POST were still refused with 403 (`s3-preflight-before-restart`, `s3-post-with-origin-before-restart`); after the game was restarted they passed (`s3-preflight`, `s3-post-with-origin`).
- **The preflight.** `OPTIONS /` with the allowlisted origin, `Access-Control-Request-Method: POST` and `Access-Control-Request-Headers: content-type, accept, mcp-session-id` is answered `204 No Content` with `Access-Control-Allow-Origin: http://localhost:4173` (the request's origin), `Vary: Origin`, `Access-Control-Allow-Methods: POST, GET, OPTIONS` and `Access-Control-Allow-Headers: Content-Type`, and nothing else from CORS: no `Access-Control-Max-Age`, no `Access-Control-Allow-Credentials` (`s3-preflight`).
- **The POST's CORS headers.** A POST with the allowlisted origin carries the same four headers; there is no `Access-Control-Expose-Headers` on it or on any other answer (`s3-post-with-origin`, all fixtures). `Access-Control-Allow-Methods` and `Access-Control-Allow-Headers` are on every answer, the 202 and the 403s included; `Access-Control-Allow-Origin` and `Vary` only on answers to an allowlisted `Origin` (`s3-preflight`, `s3-post-with-origin`, `s3-post-startup-timeout`), never without an `Origin` (`s1-*`, `s2-host-*`, `s4-*`) and never on a 403.
- **The start-up timeout.** While the restarted game was starting, `initialize` with the allowlisted origin was answered `200 OK` with the CORS headers and the JSON-RPC error `{"code":-32603,"message":"Request timed out waiting for game thread"}` (`s3-post-startup-timeout`). How long the listener waited before answering was not recorded.
- **list_chips without an IC editor.** With no IC editor open, `list_chips` answered with 23 chips on one network, each `is_selected: false` (`s4-list-chips-editor-closed`). Each entry's keys, in order: `ref_id`, `is_lua`, `is_library`, `has_error`, `is_selected`, `source_length`, `source_version`, `housing_name`, `is_on`, `housing_ref_id`, `housing_type`, `network_id`, `screen_size` (`{surface, w, h}`, present on the 12 screen hosts and absent on the 11 `CircuitHousing` entries), `modules`, `loaded_libraries`. The answer is one text block holding a JSON array.
- **set_chip_code.** Success is one text block holding JSON: `success`, `ref_id`, `mode` (`editor_then_chip`), `editor_synced` (false), `editor_sync_path` (`none`), `editor_sync_reason` ("chip is not currently selected in the in-game IC editor dropdown"), `source_version` (`s4-set-chip-code-test-chip`). A ref the session cannot reach is answered HTTP 200 with a JSON-RPC result whose one text block reads `Error: chip <ref> is not accessible from the current editor session`, with no `isError` field and no JSON-RPC error (`s4-set-chip-code-inaccessible`).
- **vector_stats.** One text block of plain text with CRLF line ends, the first line `ScriptedScreensVector 0.11.118.0`, then a block per scene (`scene "<id>" (under "<prefab>")`, nodes, rebuilds, on-screen size, projection, problems); with `scene` only that scene (`s4-vector-stats-all`, `s4-vector-stats-scene`).
- **Captures return paths.** `capture_scripted_screen` answers with one text block holding JSON, never an image block. With `ref_id`: `success`, `ref_id`, `housing_name`, `surface`, `path`, `width`, `height`, `version`, `hint` (`s4-capture-ref`). With `all: true`: `success`, `ref_id`, `captures` (each `surface`, `path`, `width`, `height`, `version`), `errors`, `hint`, `housing_name` (`s4-capture-all`). Each `path` was an absolute Windows path to a PNG in the user's temporary folder. Both captures were taken seconds after `set_chip_code` had replaced the test chip's source with an export that contains no `ss.ui.allow_mcp_automation` (none in the recorded request), and both succeeded.
- **The four schemas** are as `s1-tools-list` lists them: `list_chips` takes none; `set_chip_code` requires `ref_id` (number) and `source` (string), with an optional `mode`; `vector_stats` takes an optional `scene`; `capture_scripted_screen` takes optional `ref_id`, `surface`, `surfaces` and `all`.

**Inferred, not measured:**
- That every Host was accepted because `AllowRemoteConnections` was on. StationeersLua's guide says the listener validates `Host`; with `AllowRemoteConnections = false` the Host handling was not tried.
- From the Fetch standard, not tried in a browser: a browser request may send `Content-Type: application/json` (allowed) and this `Accept` (a safelisted header), but not `Mcp-Session-Id`, which the preflight does not allow; a browser cannot read the 403 body or the status of a refused origin, since that answer has no `Access-Control-Allow-Origin`, so the page sees a failed fetch; with no `Access-Control-Expose-Headers`, a browser could not read an `Mcp-Session-Id` even if one were sent.
- That a capture does not need the script's opt-in: the chip's source at the time had none and the capture succeeded; whether the chip had already run the new source when it was captured was not recorded.
- That the list's scope came from a chip-access setting rather than the IC editor; which one was not recorded.

**The plan's section 4 "Not verified" items:**

| Item | Settled by |

The section's other endpoint items, "observed by the M3–M5 in-game sessions, not recorded": the POST to `/` and `initialize` (`2024-11-05`), `notifications/initialized`, `tools/call` order is now recorded (`s1-*`, `s4-*`); the answer is JSON, not an event stream; no `Mcp-Session-Id` came back; a refusal arrives as a text block beginning `Error:` with no error field (`s4-set-chip-code-inaccessible`); "`list_chips` fails unless the player is at an IC editor" did not hold on this game (`s4-list-chips-editor-closed`). Not observed: `list_chips` with the IC editor open (only the closed case was recorded, and it answered), and refs changing when the world reloads (the game was restarted between `s3-*-before-restart` and `s3-preflight`, but no ref was recorded before the restart).

### The editor, chip selection and devices (plan Task 9)

Measured on 2026-10-12 with the same game, mods and save, in two game sessions: the first with `EnableExtensionApi = true`, the second after a restart with `EnableExtensionApi = false` (put back afterwards; the settings file was restored byte for byte). `AllowNetworkChipAccess = true`, `AllowNetworkChipAccessOnlyForWirelessBoards = false`. No player was at an IC editor in either session. The fixtures are `s5-*` and `s6-*` in `web/test/fixtures/game-mcp/`, scrubbed as that folder's README says.

**Observed:**
- **`get_editor_state` without a selected chip** answers one text block of JSON: `editor_open`, `allow_network_chip_access`, `allow_network_chip_access_only_for_wireless_boards`, `allow_personal_area_network_chip_access`, `mcp_debug_tools_available`, `mcp_debug_tools_reason`, `wireless_remote_access_only`, `pan_remote_access_only`, `selected_chip_ref_id`, `selected_housing_ref_id`, `selected_housing_name`, `network_id`, `network_ids`, `network_names` (an object from network id to name), `accessible_chip_count`, `selected_chip_debugger_available`, `selected_chip_debugger_reason` (`s5-editor-state-no-chip-selected`). With nobody at an IC editor it answered `editor_open: true`, `wireless_remote_access_only: true`, the three `selected_*` fields `null`, and `accessible_chip_count` 23, the length of `list_chips`. So `editor_open` true does not mean a player is at an IC editor; a selected chip shows only in `selected_chip_ref_id`. The network's name was its wireless access point's display name.
- **The editor tools without a selected chip** answer a text block beginning `Error:`: `get_editor_code` "no chip is currently selected in the editor", `set_editor_code` "chip <ref> is not the currently selected chip in the editor" (`s5-editor-code-no-chip-selected`, `s5-set-editor-code-not-selected`).
- **`set_chip_code`'s modes** without a selected chip: `editor_then_chip` exports and answers `editor_synced: false`, `editor_sync_path: none` with the reason "chip is not currently selected in the in-game IC editor dropdown"; `chip` exports and answers `editor_sync_path: not_attempted` with an empty reason; `editor_only` does not export and answers `success: false`, `exported: false` with no `source_version`; with no `mode` the answer names the mode taken (`s5-set-chip-code-*`). `source_version` went up by one on every export, the same source included.
- **`EnableExtensionApi = false`**: `tools/list` loses the four debugger tools (`get_debug_session_state`, `get_debug_stack_trace`, `get_debug_scopes`, `get_debug_variables`), 26 tools; `get_editor_state` answers `mcp_debug_tools_available: false` with the reason "debugger MCP access requires both [MCP Server] Enabled = true and EnableExtensionApi = true." (`s5-editor-state-extension-api-off`). With no `mode`, `set_chip_code` takes `chip`; with `mode: editor_then_chip` it is accepted, exports and answers as with the extension API on (`s5-set-chip-code-default-extension-api-off`, `s5-set-chip-code-editor-then-chip-extension-api-off`).
- **Devices.** `get_all_network_devices` answers one text block holding a JSON array of networks, each `network_id` and `devices`; each device `ref_id`, `prefab_hash`, `display_name`, `prefab_name`, in that order (`s6-all-network-devices`). `get_network_devices` with a `network_id` answers that network's devices as a bare array, the same entries in the same order (`s6-network-devices`). The list holds every device on the network: consoles, computers, IC housings, a gas sensor, logic memory, a wall light and the wireless access point.
- **Labelled and unlabelled devices.** Two devices carry a Labeller name: an IC housing (`Housing B`) and a 2×1 console (`Console I`), each beside other devices of the same prefab that show another name. Whether `Console H`, the only device of its prefab, carries one was not determined. An unlabelled device's `display_name` is a plain name such as the gas sensor's (`Device C`); ten IC housings share `Housing A`, the same name `list_chips` gives them as `housing_name`. That the shared names are the prefabs' default names is inferred from their being shared, not checked against the game's own names.
- **A console's board name.** For a console's ScriptedScreens board, `list_chips`' `housing_name` was the console's display name followed by ` (Scripted Screens)`, a Labeller name included (`Console I`'s board is `Console I (Scripted Screens)` in `s6-list-chips-after-reload`).
- **Refs survive a reload of the save.** After the game was closed and the save loaded again, `list_chips` and `get_all_network_devices` answered the same refs, housings, network and names (`s6-list-chips-after-reload` against `s4-list-chips-editor-closed`, which Task 1 recorded in an earlier session; `s6-all-network-devices-after-reload` against `s6-all-network-devices`). The save file loaded in both sessions was the one the game wrote during Task 1's session; it was not written again (its sha256 was the same before and after). `source_version` started at 1 after each load.

**Not observed** (the reason in each):
- `get_editor_state`, `list_chips` (`is_selected`), `get_editor_code` and `set_editor_code` with the test chip selected in the IC editor, and `set_chip_code` in `editor_then_chip` answering `editor_synced: true`, with the extension API on or off: needs a player at the IC editor. No MCP tool opens one. So whether `editor_then_chip` syncs an open editor with the extension API off is not recorded; that it is accepted and exports is.
- The scope with no wireless development board (`wireless_remote_access_only` false, no editor): the save's player has the board; taking it off needs a player.
- A world save made in the session and reloaded: no MCP tool saves the world, and closing the game did not write the save. The reload above loaded a save the game wrote earlier.
- A device rebuilt: the owner's fact (2026-10-12) is that a device's ref id changes when the device is rebuilt; not tried.

## Launch

The site is live at https://gruffuss.github.io/StationeersConsoleBuilder/, deployed from the public repository's `main` (2026-10-13). The owner confirmed it works end to end. The evidence, by kind:

### Offline
- The last gates on the private tree at `350c1fb`: all six suites exit 0 (publish, precore, `tsc -b`, vitest 249 files with 4,036 passed and 1 skipped, the build, the C# suite `ALL PASS`).
- The public tree: vitest 4,037 passed and 1 skipped (one more test: the path check's `worktrees` rule), the other suites exit 0; the build output's path check read 123 files and found zero local paths.

### CI
- The first public run on GitHub Actions, run 38318128299, on a push to `main`. The build job passed every step: type-check, web tests, the build under the project path, core tests and the Pages upload. The deploy job took 8 s.
- GitHub's note on that run: the `ubuntu-latest` label moves to Ubuntu 26 from 2026-10-19.

### Browser
- The live site loads: `core ready in 205 ms`. Every fingerprinted `_framework` file answers 200; `.wasm` files are served as `application/wasm` and `dotnet.js` as `application/javascript`. The bundled fonts and the notices load under the base path.
- A share link of 486 characters opened in a fresh tab and the project loaded. The eight share-size rows of the M4 report were not measured again.
- First load is about 3.3 MB over the wire: the page's 811 KB plus 25 core files of 2,448 KB (5,698 KB uncompressed). This is the measurement OQ8 (a) asked for; no code split was made.
- Through the development proxy (`npm run dev`): linking a chip by name, the IC-editor case, Send, and the device picker writing `prefabs` and `label` but no ref; no id showed anywhere.
- The built site served at `http://localhost:4173`, with that origin allowed in the game: Send worked. With the origin not allowed, and with the game closed, the panel listed the possible causes instead of guessing one.

### In game
- Send from the live site in the owner's Chrome. The owner: "getting chips works in chrome", "pushing works flawlesly".
- A desktop app's built-in browser pane refuses a public page's requests to `127.0.0.1` (`net::ERR_BLOCKED_BY_CLIENT`); that is the pane, not the site.
- The game's preflight answer allows `https://gruffuss.github.io` but sends no `Access-Control-Allow-Private-Network` header; Chrome accepted it anyway.
