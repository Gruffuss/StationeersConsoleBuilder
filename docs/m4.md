### R13 honest large-file memory/time

The fixture was generated by streaming ASCII through gzip, without holding its expanded producer string: **1,610,612,663 expanded bytes**, an honest ISIZE of `3L−1`, **1,565,470 gzip bytes**, **2,087,331 Lua file bytes**. Chrome's measured repeat/string limit was **L = 536,870,888 UTF-16 units**. The actual project-file path rejected it at that engine string limit, before project parsing. **The tab survived.** This is a platform-boundary rejection, not a builder cap or an invalid-scene verdict.

The observed UI interval was **1,231 ms**. Windows process samples summed private bytes and working set for this browser's process IDs, before the file read and during/after it. Samples were **629 ms** and **602 ms** apart; the requested 250 ms delay plus process-query cost accounts for the coarser observed cadence. This is sampled whole-browser process memory, not an exact decoder-heap peak. The baseline includes the preceding deep-file check and its editor state.

| Sample | Private bytes | Working set bytes |
|---|---:|---:|
| Before honest-file read | 1,348,562,944 | 1,505,230,848 |
| During read | 2,405,662,720 | 2,561,732,608 |
| Observed peak / after result | 2,874,359,808 | 3,031,625,728 |

Large compressed blocks can therefore consume substantial memory even with correct engine/ISIZE bounds. No fabricated size ceiling was introduced. A tab death would require a bounded-heap decoder item; this Chrome run did not die. Other engines and lower-memory devices remain unverified.
